# サーバマシン構築手順

## 1. 時刻同期設定(NTPサーバ)

サーバマシンをNTPサーバとして設定し、ロボット搭載マシン、robodjなど同じネットワーク内のマシンに時刻を配信する。  
サーバマシン自身は、公開NTPサーバ(ntp.nict.jp)に時刻同期する。

1. 以下のコマンドを実行し、chronyをインストールする。
   ```
   sudo apt install -y chrony
   sudo systemctl enable chrony
   ```

2. 以下のコマンドを実行し、設定ファイルのバックアップを作成する。
   ```
   sudo cp -p /etc/chrony/chrony.conf /etc/chrony/chrony.conf.old
   ```

3. /etc/chrony/chrony.confを開き、既存のpool行をコメントアウトして、以下のように同期先と配信先の設定を追加する。
   ```
   sudo vi /etc/chrony/chrony.conf
   ```

   ```
   #pool ntp.ubuntu.com        iburst maxsources 4
   #pool 0.ubuntu.pool.ntp.org iburst maxsources 1
   #pool 1.ubuntu.pool.ntp.org iburst maxsources 1
   #pool 2.ubuntu.pool.ntp.org iburst maxsources 2
   pool ntp.nict.jp iburst
   allow 192.168.0.0/24
   ```

   ※`pool`には、サーバマシンが同期する上位のNTPサーバを設定する(ネットワークに合わせて適切に設定すること)。  
   ※`allow`には、時刻を配信するネットワーク(ロボット搭載マシンなどが接続しているネットワーク)を設定する(`192.168.0.0/24`は例)。

4. 以下のコマンドを実行し、設定を反映して時刻同期状態を確認する。  
   `Reference ID`が上位のNTPサーバで、`Leap status`が`Normal`であれば正常。
   ```
   sudo systemctl restart chrony
   chronyc tracking
   ```

5. ロボット搭載マシンなどの時刻同期設定後、以下のコマンドを実行し、同期しているマシンが一覧に表示されることを確認する。
   ```
   sudo chronyc clients
   ```

## 2. Avahi設定

Avahiにより、ロボット搭載マシンなどからサーバマシンを`<ホスト名>.local`で名前解決できるようにする。  
(mongo.envの`MONGO_PUBLIC_HOST`や、ロボット搭載マシンの`MONGO_URI`に`<ホスト名>.local`を使用する場合に必要)  
設定するネットワークインタフェースはマシンごとに異なるため、マシンごとに確認して設定すること。

1. 以下のコマンドを実行し、Avahiをインストールする。
   ```
   sudo apt install -y avahi-daemon
   sudo apt install -y avahi-utils
   ```

2. 以下のコマンドを実行し、他のマシンと通信するネットワークインタフェースの名前を確認する。  
   インタフェース名はマシンごとに異なる(e.g. `enp2s0`、`enp0s31f6`、無線LANの場合は`wlp3s0`など)。  
   他のマシンと同じネットワークのIPアドレスが割り当てられているものを選ぶ。
   ```
   ip -br addr
   ```

   ※Docker(「5. MongoDBの構築」でインストール)をインストール済みの場合、Dockerが作成する仮想インタフェース(`docker0`、`br-xxxx`、`vethxxxx`)も表示されるが、これらは選ばないこと。  
   　仮想インタフェースでもホスト名を公開すると、名前の衝突により`<ホスト名>-2.local`のように名前が変わることがある。

3. /etc/avahi/avahi-daemon.confを開き、以下の通り設定を編集する。  
   `allow-interfaces`には、手順2で確認したインタフェース名を設定する(`enp2s0`は例)。
   ```
   sudo vi /etc/avahi/avahi-daemon.conf
   ```

   ```
   use-ipv4=yes
   use-ipv6=no
   allow-interfaces=enp2s0
   ```  

4. 以下のコマンドを実行し、設定を反映させる。
   ```
   sudo service avahi-daemon restart
   ```

5. 他のマシンから以下のコマンドを実行し、本マシンのホスト名(`<ホスト名>.local`)でIPアドレスが引けることを確認する。
   ```
   avahi-resolve -n <本マシンのホスト名>.local
   ```

## 4. 環境変数設定

MongoDBの構築、ビルド、起動スクリプトはいずれも環境変数を参照するため、これらより先に本設定を行うこと。  
以下の作業はホスト上(コンテナ外)で実施する。

1. 以下のコマンドを実行し、guardian_robot_system/indy.env.sampleをコピーして~/indy.envを作成する。
   ```
   cp <guardian_robot_systemのパス>/indy.env.sample ~/indy.env
   ```

2. ~/indy.envを開き、以下の項目をサーバマシン用に設定する。
   ```
   vi ~/indy.env
   ```

   |変数名|設定値|
   |---|---|
   |ON_ROBOT|空のまま(`1`を設定しないこと)<br>※`1`以外の場合、ロボット専用パッケージはビルドされず、zenoh-bridge-ros2ddsはサーバ側として起動する。|
   |GUARDIAN_ROBOT_PATH|guardian_robot_systemリポジトリのパス|
   |ROBOT_NAME|接続するロボットのロボット名|
   |MONGO_URI|MongoDBのホスト名またはIPアドレス(本サーバのホスト名。ロボット搭載マシンから名前解決できる名前を設定)<br>※「5. MongoDBの構築」のmongo.envの`MONGO_PUBLIC_HOST`と同じ値にする。|
   |MONGO_PORT|MongoDBのポート番号(e.g. 9110)<br>※「5. MongoDBの構築」のmongo.envの`MONGO_PORT`と同じ値にする。|
   |ROS_DOMAIN_ID|ROS_DOMAIN_ID(ロボット搭載マシンと同じ値を設定)|
   |ZENOH_ROBOT_ADDR|接続先ロボット搭載マシンのIPアドレス(必須)|
   |ZENOH_PORT|zenohのポート番号(任意。ロボット搭載マシンと同じ値を設定。空の場合は7447)|
   |OPENAI_API_KEY|OpenAIのAPIキー(llm_responder、memoryで使用)|
   |DEEPL_API_KEY|DeepLのAPIキー(chat_monitorを使用する場合のみ)|
   |ASR_GPU_ID|音声認識(50_grsrv_asr)で使用するGPU番号(未設定時は3)<br>※**GPUが4枚未満のマシンでは設定必須**(e.g. GPUが1枚の場合は`0`)。|
   |CUDA_VISIBLE_DEVICES|使用するGPU番号(任意。ssl_server.launch.pyで使用。未設定時は3)|

   ※`RMW_IMPLEMENTATION`、`CYCLONEDDS_URI`はサンプルの値から変更しないこと。  
   　マシン間の通信はzenoh-bridge-ros2ddsが中継する。  
   ※音声認識のGPU番号の既定値(3)は、GPUが4枚以上の構成を前提としている。GPUが4枚未満のマシンでは`ASR_GPU_ID`を必ず設定すること。  
   　GPUの枚数と番号は、`nvidia-smi -L`で確認できる。

3. .bashrcを開き、以下の設定を追加する。
   ```
   vi ~/.bashrc
   ```

   ```
   # Indy
   source ~/indy.env

   # ROS2 (コンテナ内のみ)
   if [ -n "$APPTAINER_CONTAINER" ]; then
       source /opt/ros/humble/setup.bash
       if [ -f "$GUARDIAN_ROBOT_PATH/ros2_ws/install/local_setup.bash" ]; then
           source "$GUARDIAN_ROBOT_PATH/ros2_ws/install/local_setup.bash"
       fi
   fi
   ```

   ※~/.bashrcはホストとコンテナで共有される。ホストにはROS2をインストールしないため、ROS2関連の読み込みはコンテナ内でのみ行う。  
   ※ビルド結果(install/local_setup.bash)は「7. ソフトウェアのビルド」の後に読み込まれるようになる。

4. 以下のコマンドを実行して設定を反映し、環境変数が設定されていることを確認する。
   ```
   source ~/.bashrc
   echo $GUARDIAN_ROBOT_PATH $ROBOT_NAME $ROS_DOMAIN_ID $ZENOH_ROBOT_ADDR
   ```

   ※起動スクリプトは、tmuxが起動した時点の環境変数を引き継ぐ。後から~/indy.envを変更した場合は、`~/module_launch/kill_sessions.sh`で全セッションを停止して`tmux kill-server`を実行し、新しいターミナルから起動し直すこと。

## 5. MongoDBの構築

MongoDBはDocker上で動作させる。  
本章の構成は`setup/mongo_docker`にある。詳細(既存データの移行、1台のサーバで複数ロボット分を動かす方法など)は[setup/mongo_docker/README.md](../../setup/mongo_docker/README.md)を参照。

1. 以下のコマンドを実行し、Docker と Docker Compose(`docker compose`コマンド)をインストールする。  
   ※既にDockerがインストールされており、`docker compose version`が実行できる場合は不要。
   ```
   sudo apt update
   sudo apt install -y docker.io docker-compose-v2
   docker compose version
   ```

2. 以下のコマンドを実行し、マシン起動時にDockerが自動で起動するよう設定する。  
   また、sudoなしでdockerコマンドを実行できるよう、ユーザをdockerグループに追加する。
   ```
   sudo systemctl enable --now docker
   sudo usermod -aG docker $USER
   ```

   ※グループの追加は再ログイン後に反映される。一度ログアウトし、再度ログインすること。

3. 以下のコマンドを実行し、mongo.envを作成する。
   ```
   cd $GUARDIAN_ROBOT_PATH/setup/mongo_docker
   cp mongo.env.sample mongo.env
   ```

4. mongo.envを開き、以下の項目を設定する。
   ```
   vi mongo.env
   ```

   |変数名|設定値|
   |---|---|
   |MONGO_PUBLIC_HOST|本サーバのホスト名またはIPアドレス<br>※~/indy.envの`MONGO_URI`と同じ値にする。|
   |MONGO_PORT|MongoDBのポート番号(e.g. 9110)<br>※~/indy.envの`MONGO_PORT`と同じ値にする。|
   |ME_PORT|MongoDB管理画面(Mongo Express)のポート番号(e.g. 9111)|
   |ME_BIND_ADDR|`0.0.0.0`(サンプルの値のまま)<br>※同じネットワーク内の他のマシンのブラウザから管理画面を開けるようにする設定。<br>　管理画面には認証が無いため、信頼できるネットワーク外からアクセスされる環境では`127.0.0.1`(本サーバ上のブラウザからのみ開ける)にすること。|
   |MONGO_IMAGE|`mongo:8.0`(サンプルの値のまま)|
   |MONGO_DATA_DIR|データの置き場所(e.g. `/home/<ユーザ名>/robots_memory/mongodb`)<br>※リポジトリの外に置くこと。|
   |MONGO_UID / MONGO_GID|MongoDBを動かすユーザのuid / gid(サンプルの値のままで可)|

5. 以下のコマンドを実行し、データディレクトリを作成する。  
   ※MongoDBを起動する前に必ず作成すること。作成せずに起動すると、MongoDBが書き込めず起動に失敗する。
   ```
   ( set -a; . ./mongo.env; set +a
     mkdir -p "$MONGO_DATA_DIR"/{data,config,var_cache}
     sudo chown -R "$MONGO_UID:$MONGO_GID" "$MONGO_DATA_DIR" )
   ```

   ※`( ... )`のサブシェルで実行し、mongo.envの値をシェルに残さないようにしている。

6. 以下のコマンドを実行し、MongoDBを起動する。  
   ※`docker compose`のコマンドには、毎回`--env-file mongo.env`を付けること。
   ```
   docker compose --env-file mongo.env config -q
   docker compose --env-file mongo.env up -d
   ```

7. 以下のコマンドを実行し、起動したことを確認する。  
   mongoの状態が`(healthy)`になれば起動完了(初回は20〜30秒ほどかかる)。
   ```
   docker compose --env-file mongo.env ps
   ```

8. 以下のコマンドを実行し、標準データ(パラメータ、シナリオ、プロンプト、声、動作など)を投入する。  
   ※既存環境のデータを持ち込む場合は不要。README.mdの「既存データの持ち込み」を参照。
   ```
   ./import_default_data.sh $ROBOT_NAME
   ```

9. 投入後に表示されるプレースホルダ(`__LLM_HOST__`など)を、管理画面で環境に合わせて書き換える。  
   管理画面は、ブラウザで`http://<MONGO_PUBLIC_HOST>:<ME_PORT>/`を開く。  

   |プレースホルダ|場所(データベース.コレクション)|内容|
   |---|---|---|
   |`__LLM_HOST__`|robot_config.system_parameters(memory / llm_responder)、rism_configs.rism_config|LLMサーバ(OpenAI互換API)のホスト|
   |`__EMBED_HOST__`|robot_config.system_parameters(memory / llm_responder)|埋め込みAPIのホスト|
   |`__TTS_HOST__`|persona.Voice|音声合成サーバのホスト(`type`が`hoya`のとき使用)<br>※標準データの`type`は`gtts`(Google音声合成)のため、変更しない場合は書き換え不要。<br>※音声合成サーバは本リポジトリに含まれないため、`hoya`を使う場合は別途用意する。|
   |`__ADIN_SERVER__`|robot_config.system_parameters(asr)|音声認識の入力(adintool)サーバのIPアドレス|
   |`__AUDIO_IP__`|robot_config.system_parameters(ros_audio_tracker)|音声の送り先のIPアドレス|
   |`__GOOGLE_ASR_SERVER__`|rism_configs.rism_config|Google音声認識中継サーバのIPアドレス|
   |`__OPENWEATHERMAP_TOKEN__`|rism_configs.rism_config|OpenWeatherMapのAPIキー(天気の話題で使用)|

※MongoDBと管理画面のコンテナは、マシンの再起動後も自動で起動する(Dockerの自動起動と、コンテナの`restart: always`設定による)。  
　ただし、`docker compose ... down`を実行するとコンテナが削除され、自動起動しなくなる。一時的に止める場合は`stop`を使用し、`down`した場合は手順6を再度実行すること。

## 6. Apptainerの設定

1. 以下の手順でApptainerをインストールする。  
   https://apptainer.org/docs/admin/main/installation.html#install-ubuntu-packages

2. 以下のコマンドを実行し、ビルド前の設定を行う。
   ```
   cd $GUARDIAN_ROBOT_PATH/setup/container_image

   export APPTAINER_TMPDIR=/var/tmp/apptainer-build
   export APPTAINER_CACHEDIR=/var/tmp/apptainer-cache

   mkdir -p /var/tmp/ros2_va_tmp
   chmod 1777 /var/tmp/ros2_va_tmp

   mkdir -p /var/tmp/fakehome

   export HOME=/var/tmp/fakehome
   export DOCKER_CONFIG=/var/tmp/empty-docker
   ```

3. 以下のコマンドを実行し、コンテナイメージをビルドする。
   ```
   apptainer build \
    --notest \
    --mount type=bind,src=/var/tmp/ros2_va_tmp,dst=/tmp \
    -F ros2_12-6-3_on_server.sif \
    ros2_12-6-3_on_server.def
   ```

4. 以下のコマンドを実行し、生成したコンテナイメージのテストを実行する。
   ```
   apptainer test --nv ros2_12-6-3_on_server.sif
   ```  

   以下のように表示され、`FAIL`、`NG`、`NUMPY NOT 2.x`が表示されなければテスト成功(以下は主な表示の抜粋。バージョンは環境によって異なる)。
   ```
   --- numpy / opencv ---
   numpy 2.x.x
   cv2 4.x.x
   numpy2 ok

   --- cv_bridge (numpy2 rebuild) ---
   cv_bridge OK (numpy2 ABI) ...

   --- torch ---
   torch 2.x.x+cu126 tv 0.x.x cuda built: 12.6

   --- ROS ---
   rclpy OK
   nav2_msgs OK
   ros2 CLI OK
   zenoh bridge OK

   --- onnxruntime (rtmlib 用) ---
   providers: ['CUDAExecutionProvider', ...]
   session providers: ['CUDAExecutionProvider', ...] -> GPU OK

   --- misc imports ---
     ok   ...
     ok   trackers.ByteTrackTracker (supervision 0.x.x)
   ```

5. 2.で移動したディレクトリ(setup/container_image)で以下のコマンドを実行し、生成したコンテナイメージを起動する。
   ```
   apptainer shell --nv ros2_12-6-3_on_server.sif
   ```

   以下のようなプロンプトが表示されれば起動成功。
   ```
   Apptainer>
   ```

6. 起動したコンテナ上で、以下の確認を行う。
   - GPUの状態確認  
     NVIDIA製のGPUの状態を確認する。  
     以下のコマンドを実行し、実行結果例のように表示されることを確認する。
     - 実行コマンド  
       ```
       nvidia-smi
       ```
     - 実行結果例
       ```

       |-------------------------------+----------------------+----------------------+
       | GPU  Name        Persistence-M| Bus-Id        Disp.A | Volatile Uncorr. ECC |

       |   0  NVIDIA RTX 3090     Off  | 00000000:01:00.0 Off|                  N/A  |
       | 31%   42C    P8    28W / 350W |      5MiB / 24576MiB|      0%      Default  |
       +-------------------------------+----------------------+----------------------+
       ```
       ※GPU名、ドライババージョン、CUDAバージョンは環境によって異なる。

   - ROS2パッケージ確認  
     ROS2で利用可能なパッケージを確認する。  
     以下のコマンドを実行し、実行結果例のように表示されることを確認する。
     - 実行コマンド  
       ```
       ros2 pkg list
       ```
     - 実行結果例
       ```
       action_msgs
       ament_cmake
       ament_cmake_core
       ament_index_cpp
       ament_index_python
       builtin_interfaces
       class_loader
       ...
       ```

   - PyTorch確認  
     PyTorchがインストールされていて、GPUが利用できる状態かを確認する。  
     以下のコマンドを実行し、実行結果例のように表示されることを確認する。
     - 実行コマンド
       ```
       python3 -c "import torch; print(torch.__version__); print(torch.cuda.is_available())"
       ```
     - 実行結果例
       ```
       2.14.0+cu126
       True
       ```

   - cv_bridge確認  
     cv_bridgeがNumPy2環境で正常に動作するかを確認する。  
     以下のコマンドを実行し、実行結果例のように表示されることを確認する。
     - 実行コマンド
       ```
       python3 /opt/check_cv_bridge.py
       ```
     - 実行結果例
       ```
       cv_bridge OK (numpy2 ABI) numpy 2.x.x from /opt/numpy2_ws/install/...
       ```

7. 以下のコマンドを実行し、コンテナを終了する。
   ```
   exit
   ```

8. 2.で`HOME`を変更しているため、このターミナルを閉じ、以降の作業は新しいターミナルで行う。

## 8. recognitionノードの設定

1. 認識に使うモデル(物体検出、骨格推定、頭部姿勢推定、属性認識、動作認識など)は、初回起動時に自動でダウンロードされる。インターネットに接続できることを確認する。  
   ※頭部姿勢推定(`hopenet_alpha1.pkl`)など、一部のモデルは`$GUARDIAN_ROBOT_PATH/ros2_ws`に保存される(recognitionノードは`$GUARDIAN_ROBOT_PATH/ros2_ws`で起動される)。  
   ※属性認識(`attributes_pa100kb.pth`)と動作認識のモデルは、Hugging Faceから取得され、`~/.cache/huggingface`に保存される。  
   ※インターネットに接続できない環境では、接続できる環境で一度起動し、上記のファイルとキャッシュをコピーしておくこと。

2. GPUが4枚未満のマシンでは、「4. 環境変数設定」で`ASR_GPU_ID`を設定していることを確認する。  
   ※設定していない場合、音声認識(50_grsrv_asr)に存在しないGPU番号(3)が使われ、正しく動作しない。  
   ※画像認識(recognition)のGPU番号は、GPUの枚数から自動で選ばれるため設定不要。

3. 以下のコマンドを実行し、コンテナを起動する。
   ```
   cd $GUARDIAN_ROBOT_PATH/setup/container_image
   apptainer shell --nv ros2_12-6-3_on_server.sif
   ```

## 9. 起動スクリプトの準備

起動スクリプト(module_launch)と運用ツール(tools/bin)は、迷わず実行できるよう、ホームディレクトリにシンボリックリンクを作成して使用する。  
※コピーではなくシンボリックリンクを作成すること。各スクリプトはリポジトリ内の`enable`フォルダを参照するため、コピーした先の`enable`に登録したスクリプトは起動されない。

1. 以下のコマンドを実行し、ホームディレクトリにmodule_launch、bin、tmuxの設定ファイルへのシンボリックリンクを作成する。
   ```
   ln -s $GUARDIAN_ROBOT_PATH/modules/module_launch ~/
   ln -s $GUARDIAN_ROBOT_PATH/tools/bin ~/bin
   ln -s $GUARDIAN_ROBOT_PATH/modules/indy_modules/tmux/.tmux.conf ~/
   ```

   ※~/binが既に存在する場合、2行目は~/bin/binを作成してしまう。その場合は2行目の代わりに以下を実行し、個別にリンクを作成する。
   ```
   ln -s $GUARDIAN_ROBOT_PATH/tools/bin/* ~/bin/
   ```

2. 一度ログアウトし、再度ログインする。  
   ~/binはログイン時にPATHに追加される(Ubuntu標準の~/.profileの設定による)。  
   以下のコマンドを実行し、binのスクリプトが見つかることを確認する。
   ```
   which 00_module_launch.sh
   ```

3. 以下のコマンドを実行し、一括起動するスクリプトを`enable`フォルダに登録する(標準の組み合わせ)。  
   各スクリプトの概要は、[Indyソフトウェア仕様書.md](../仕様書/Indyソフトウェア仕様書.md)の「1. ソフトウェア構成」の「② サーバマシン」を参照。  
   ※起動スクリプトはホスト上(コンテナ外)で実行する。サーバマシン用のスクリプトは、自動でコンテナを起動する。
   ```
   cd ~/module_launch/enable
   ln -s ../available/000_zenoh_bridge.sh .
   ln -s ../available/50_grsrv_asr.sh .
   ln -s ../available/50_grsrv_db_management.sh .
   ln -s ../available/50_grsrv_human_tracker.sh .
   ln -s ../available/50_grsrv_llm_responder.sh .
   ln -s ../available/50_grsrv_memory.sh .
   ln -s ../available/50_grsrv_recognition.sh .
   ls -l
   ```

   ※50_grsrv_ros_asr、50_grsrv_vad_for_cameraは標準では登録しない。必要な場合のみ、上記と同様に登録する。

4. ホームディレクトリで以下のコマンドを実行し、登録したスクリプトが一括起動されることを確認する。  
   起動・終了の詳細は、[Indyマニュアル.md](../マニュアル/Indyマニュアル.md)の「2. 起動手順」「3. 終了手順」を参照。
   ```
   cd ~
   module_launch/module_launch.sh
   module_launch/check_sessions.sh
   ```
